## 0-бис. ЧТО ЗАКРЫТО ЗАМЕРОМ И К ЧЕМУ НЕ ВОЗВРАЩАТЬСЯ

* **Свёртка цепей в декоде — не байтовый рычаг**: избыточных пересечений HBM во всём шаге
  73.8 МБ = **0.47 %**; шесть верхних свёрток опровергнуты (inductor слил их раньше нас).
* **Умножения на весах — не рычаг иксов**: веса 62.5 % шага идут уже на **743 ГБ/с = 85 % крыши**;
  вся статья «GEMV ниже канала» = 9.1 % даже при идеальном ядре.
* **Префикс-кэш после 64К НЕ обваливается** (гипотеза снята замером): повтор стоит 1.47 с при 21К
  и 2.65 с при 117К — контекст вырос в 5.5 раза, повтор в 1.8.
* **Интенсивность при K=1 задана алгоритмом**: 2 Флоп/байт, и перестановкой команд её не поднять.
  Единственный рычаг через гребень 64.4 — **K токенов за проход** (интенсивность 2K, гребень при K=32).

## 0-тер. ТРИ ПРИБОРА, КОТОРЫЕ ЗА СУТКИ СОВРАЛИ (проверять ДО гипотезы)

1. **Мёртвая ручка**: литерал 64 стоял ВНУТРИ `_auto_splits`, а переменная снаружи могла только
   понизить — любой опыт с ней давал ноль и «доказывал», что потолок ни при чём.
2. **Забытый `k_absmax`**: стенд пересканировал весь KV-кэш на каждый вызов, все точки лестницы
   дали 0.9 % крыши — мерялось сканирование, а не внимание.
3. **Размах вчетверо больше эффекта**: сквозной стенд с ±10 % не мог различить 2.7 %. После
   CUDA-графа размах стал **±0.3 %**, и тот же вопрос стал измерим.
4. **Вырожденная метрика попадания**: «49.5 % в паре» — это структура моего теста (один промах +
   одно попадание), а не свойство кэша.

## 1. ЕДИНИЦЫ (в них обязан быть сформулирован любой довод)

| единица | смысл | чем НЕ является |
|---|---|---|
| **ФАЗА** | множество операций, занимающее КАНАЛ на промежутке | не команда, не ядро |
| **ПЕРИОД** | max по каналам (нагрузка / ёмкость) | не сумма работы |
| **ПРЕВЫШЕНИЕ** | то, что минимизируется | не «ускорить всё» |
| **СОБЫТИЕ ПЕРЕВОЗКИ** | обращение к памяти | не байт |
| **РАСПИСАНИЕ** | сумма полей задержки по телу | не счёт команд |
| **ЯЧЕЙКА** | единица регистрового учёта (`LDS.U.128 R24` = R24..R27) | не имя регистра |

**Признак нарушения:** довод, в котором нет ни одной из этих единиц и ни одного нашего числа,
взят не отсюда.

## 2. ЧИСЛА, НЕСУЩИЕ РЕШЕНИЯ (все замерены, источник указан)

**Раскладка токена декода** (CUPTI изнутри графа, 63K, TP=2; `SPEC_DECODE.md` §2.1):
веса **62.5 %**, внимание 13.4 %, обмен 6.7 %, мелкие ядра + зазоры 11.3 %, скан GDN 4.1 %.
Сумма сходилась и при ПОЛНОСТЬЮ неверной структуре — проверять слагаемые, не итог.

**Декод связан перевозкой — замерено прямо** (`reports/EV_decode_yarus0_clocks.md`):
+18.6 % такта дают **+1.7 %** при 1.3K и **+8.4 %** при 251K. Упругость 0.09 / 0.45.
Значит на статье весов ход, ускоряющий счёт, даёт почти ноль; берётся только СОКРАЩЕНИЕМ БАЙТ.

**База стенда** (карты 0-1, частота зафиксирована 1530): **31.45-32.05 / 25.41-25.47 / 21.15-21.30**
ток/с на 1262 / 133322 / 251122 токенов. **Шумовой пол: 1.9 % / 0.2 % / 0.7 %** — сдвиг меньше
этого не является результатом.

**Регистровый обрыв боевого декодного тела** `<EPT=8, KVB=87(e4m3), GF=6>`:
`REG:168, SHARED:24768, LOCAL:0`. Порог трёх блоков на SM = `65536/(3*128) = 170.67`.
**168 — это ровно край.** Любая правка, добавляющая регистры, роняет занятость на треть.

**Конвейер закрыт замером** (`reports/EV_decode_pipeline_pf_uu.md`): углубление 6 -> 10 широких
загрузок ценой 3 -> 2 блоков даёт 0.997 / 0.988 / 1.002 — внутри шума. Два множителя Литтла
исчерпаны, остаётся ТРЕТИЙ: ширина запроса.

**Потолок мегаядра посчитан ДО постройки** (`PLAN_FUSED_KERNELS.md` §0): режим A +2.1…2.5 %,
режим B отрицателен арифметически, режим C запрещён правилом П3. Налог существования запусков
**0.784 мс = 2.5 %** — меньше цели.


**Два хода подряд подтвердили закон фазы** (`reports/EV_decode_pipeline_pf_uu.md`,
`reports/EV_decode_wide_q_prologue.md`): конвейер (глубина 6 -> 10) и события перевозки в прологе
(48 -> 6 при НУЛЕВОЙ цене по регистрам) — оба улучшили измеримую величину в верную сторону и оба
дали РОВНО НОЛЬ, потому что улучшали фазу ВНЕ ПЕРИОДА. Проверять надо тело цикла, не пролог.

## 3. ЗАКОНЫ, КОТОРЫЕ ОТМЕНЯЮТ ОБЩЕЕ ЗНАНИЕ

1. **Тень прячет ЗАДЕРЖКУ, но не НАГРУЗКУ канала.** Где период задаёт нагрузка, укладка приза не даёт.
2. **Расписание = 2*nHMMA − (HMMA, за которыми идёт нетензорная) + Σ задержек нетензорных.**
   Поле задержки задаёт КЛАСС СЛЕДУЮЩЕЙ команды; идеально перемежённая нетензорная стоит НОЛЬ.
3. **В дефиците теней пол укладки = тени + предметы = канал ВЫДАЧИ** (22 тела из 25), и рычагом
   становится СОКРАЩЕНИЕ числа команд, а не расстановка.
4. **Слияние сводить ПО ФАЗАМ.** Сливать имеет смысл тела, у которых период задают РАЗНЫЕ каналы;
   тела на одном канале складывают нагрузку и берут max по регистрам — приза нет по построению.
5. **Формат выбирают по ЦЕНЕ РАЗВОРОТА, а не по числу байт** (14.7 % времени за команду на элемент).
   Чётные ширины байтово выровнены; int14 бьёт fp16 по обеим осям; потолок одного прохода 10 бит.
6. **Мера слияния — счёт на СОБЫТИЕ перевозки, а не байты.**

## 4. ГРАНИЦЫ И ЗАПРЕТЫ (нарушение = потерянный прогон или упавший бой)

* карты 2-3 — БОЕВОЙ сервер :8085; не трогать, не мерить на них, ничего не запускать;
* **никогда не снимать по шаблону** (`pkill -f`): шаблон совпадает с родительской оболочкой живого
  сервера и с собственной командой уборки. Опознавать процесс по ПОРТУ из `cmdline` и по тому,
  какую КАРТУ он занимает (`nvidia-smi -i 0,1 --query-compute-apps`), а не по `environ`
  (у `VLLM::Worker` переменной `CUDA_VISIBLE_DEVICES` там НЕТ ВОВСЕ);
* **не удалять файл замка** — `rm -f` обесценивает `flock`, следующий берёт замок на новом inode;
* окружение сборки ЗАДАВАТЬ, а не наследовать (`${VAR:-...}` не срабатывает ровно тогда, когда нужен);
* маршрут доказывать ПОВЕДЕНИЕМ: запрошенный бэкенд движок может молча отбросить;
* замер без ЗАФИКСИРОВАННОЙ частоты недействителен; замер по шине — только на паре 2-3.
