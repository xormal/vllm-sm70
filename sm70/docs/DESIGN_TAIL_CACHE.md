# НЕПРЕРЫВНЫЙ ХВОСТ: убрать пересчёт 1568-токенного блока на каждом ходе диалога

Проект правки внутренностей vLLM. Гейт `FA2SM70_TAIL_CACHE`, умолчание ВЫКЛЮЧЕНО.
Основание — замеры в `reports/EV_hit_recompute_1568.md`.

## 1. Что чиним (числа, не намерения)

Попадание в префикс на боевой сети стоит 1.51 с при контексте 43 308. Модель цены проверена на
четырёх точках:

    попадание = пересчёт * 1.25 мс + внимание(контекст)

| контекст | пересчёт, ток | предсказано | замерено |
|---|---|---|---|
| 5 308 | 604 | 0.78 с | 0.779 |
| 21 508 | 1 124 | 1.48 с | 1.468 |
| 43 308 | 972 | 1.46 с | 1.509 |
| 87 708 | 1 468 | 2.53 с | 2.599 |

Пересчёт есть потому, что префикс-кэш переиспользует ТОЛЬКО целые блоки, а блок здесь **1568
токенов** (навязан частным «страница состояния GDN 784 КиБ / 512 Б байтов KV на токен»).
Матожидание выброшенной работы — 784 токена на КАЖДЫЙ ход диалога.

Снятие пересчёта даёт попадание ~0.3 с вместо 1.51 — **x5 на ходе**.

## 2. Почему НЕ уменьшаем блок (закрыто замером до постройки)

Уменьшить блок внимания до 392 можно только дополнением страницы (`page_size_padded`), потому что
распределитель требует ЕДИНООБРАЗНОГО размера страницы (`is_kv_cache_page_size_uniform`). Дополнение
множит плиту KV вчетверо. Замеренная ёмкость на этой машине — **97 216 токенов** (62 блока,
concurrency 1.44x для 262K). Вчетверо меньше — 24 тысячи, и контекст 43К перестаёт помещаться.
**Путь мёртв по памяти.**

Уменьшить страницу GDN тоже нельзя: состояние уже fp16 (768 КиБ на слой, 36.0 МиБ на всю сеть на
воркер), дальше только int8 по рекуррентному состоянию — отдельный риск точности, не сюда.

## 3. Что строим

**Хвост не РАЗДЕЛЯЕТСЯ, а ПЕРЕДАЁТСЯ.** Это снимает самую тяжёлую часть (копирование при записи):
законный потребитель хвоста ровно один — следующий ход того же диалога.

При завершении запроса длиной L (промпт + ответ) запоминаем:

* неполный последний блок внимания (16 слоёв x 784 КиБ = **12.2 МиБ**);
* блок состояния GDN ровно на позиции L (48 слоёв x 768 КиБ = **36.0 МиБ**);
* ключ: `hash(родительский хэш последнего ПОЛНОГО блока, кортеж хвостовых токенов, ("tail", L))`.

Итого один индекс блока = **48.2 МиБ** на запомненный диалог. При 4-8 записях — 0.2-0.4 ГиБ, против
вчетверо большей плиты KV у отвергнутого пути.

Новый запрос после обычного поиска по целым блокам пробует продлиться хвостом: если его токены
совпадают с записанными на длине L, он ЗАБИРАЕТ блоки себе, запись отзывается, а
`num_computed_tokens` становится равен **L** — числу токенов, а не числу блоков.

Гонка двух запросов за один хвост разрешается тривиально: второй не находит записи и считает как
сейчас. Корректность от этого не зависит, только скорость.

## 4. Где ломается их модель и что именно правим

Их допущение записано в самом коде:

    allocate_slots() requires num_computed_tokens to be block-size aligned
    new_comp = len(new_computed_blocks) * block_size

«Сколько посчитано» ВЫВОДИТСЯ из числа блоков и в токенах невыразимо. Снятие этого — суть правки.

Точки:

1. `v1/core/block_pool.py` — реестр хвостов: запись, поиск, отзыв, учёт ссылок.
2. `v1/core/kv_cache_manager.py::get_computed_blocks` — после обычного поиска попытка продления;
   возврат `num_computed_tokens` в ТОКЕНАХ.
3. `v1/core/kv_cache_coordinator.py` / `single_type_kv_cache_manager.py` — принять невыровненное
   число посчитанных токенов (у внимания это уже законно при дроблёном префилле; у MambaManager
   состояние соответствует ровно L, что и есть требуемая семантика).
4. `v1/core/sched/scheduler.py` — при завершении запроса регистрировать хвост вместо освобождения.

## 5. Фальсификатор (обязателен до любого замера скорости)

Тихая неверность здесь страшнее падения: неверно восстановленное состояние GDN даёт правдоподобный,
но ДРУГОЙ текст.

1. **Побитовая сверка вывода.** Один и тот же диалог из трёх ходов при `FA2SM70_TAIL_CACHE=0` и `=1`,
   температура 0 -> совпадение токен-в-токен. Несовпадение = отказ, скорость не смотрим.
2. **Ломающая симметрию проверка.** Подменить восстановленное состояние GDN нулями: вывод ОБЯЗАН
   испортиться. Если не испортился — маршрут не исполнялся, и первая проверка ничего не доказала.
3. **Счётчик маршрута,** который пишет воркер по факту работы (`tail_hit`), а не наличие файла.
4. **Извлечение кодового слова** из НАЧАЛА длинного контекста после трёх ходов подряд.

## 6. Границы

* Гейт по умолчанию ВЫКЛЮЧЕН; боевой сервер идёт из закреплённого слепка и не затрагивается.
* Выигрыш только на ПРОДОЛЖЕНИИ диалога. Независимые запросы с общим префиксом получают прежнее
  поведение (там нужна была бы разделяемая копия, а не передача).
* Замеры хвоста снимать на тестовом стенде, помня: карты 0-1 на мосту PCIe, боевые 2-3 на NVLink,
  поэтому доля обмена на стенде завышена.
