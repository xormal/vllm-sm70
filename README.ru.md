# vLLM-SM70

[English](README.md) · **Русский**

**Боевой стек vLLM для NVIDIA Volta (V100, `sm_70`).** Он обслуживает Qwen3.8-27B (GPTQ-Int8) с
контекстом 262 144 токена на двух картах по 32 ГБ, а на тех же весах — классификатор Cloudflare
Clef.

Здесь ровно тот код, что с 12.10.2026 обслуживает боевой трафик: форк vLLM, библиотека ядер для
Volta, слой интеграции, пускач и набор рычагов работающего сервера. Это форк
[1CatAI/1Cat-vLLM](https://github.com/1CatAI/1Cat-vLLM), который сам является форком
[vllm-project/vllm](https://github.com/vllm-project/vllm) под Volta. Ветка `sm70`.

Веса модели и адаптеры Clef: **[alexxorm/Qwen3.8-27B-ABLITERATED-GPTQ-Int8-Clef](https://huggingface.co/alexxorm/Qwen3.8-27B-ABLITERATED-GPTQ-Int8-Clef)** на Hugging Face.

## Зачем

Современные ядра внимания (FlashAttention ≥ 2 — от `sm_80`, FlashInfer — от `sm_75`) и большинство
квантованных GEMM на Volta не работают. Поэтому штатный vLLM на V100 либо медленный, либо держит только
короткий контекст, а гибридные модели вроде Qwen3.5/3.8 (Gated DeltaNet + полное внимание) не
запускает вовсе. Этот стек закрывает разрыв своими ядрами и интеграцией:

* **внимание:** префилл на FMHA из CUTLASS; разреженный префилл с измеренной границей ошибки; страничный
  декод со split-K и KV-кэшем int8; виртуальный батч для позиций спекуляции. Каждое ядро сверено с
  эталоном точного softmax в fp32;
* **линейные слои:** GEMV для GPTQ-int8 на тензорных ядрах в декоде; в префилле — int8 GEMM на
  turbomind s884 и восстановление весов для cuBLAS; 12-битные (W12) проекции внимания; `lm_head` в int8;
* **гибридная модель:** пулы состояния Gated DeltaNet в int16, раздельные пулы KV, блоки, выровненные
  под 262K на 64 ГБ памяти; общие метаданные GDN для всех групп;
* **спекуляция:** собственная голова MTP модели (int8, свой CUDA-граф, аргмакс по int4-срезу
  словаря), и n-граммы, когда их приёмка выше;
* **Clef на тех же весах:** поправка весов низкого ранга для строк Clef внутри int8-ядер GEMM и голова
  на родном CUDA. Запросы Clef получают веса Clef, а чаты в том же батче остаются нетронутыми. Вторая
  модель не загружается.

## Требования

* 2× NVIDIA V100 32 ГБ (проверено на паре с NVLink и на паре через PCIe); драйвер с CUDA 12.8 (проверен 580).
  Карты должны принадлежать серверу **целиком**: план памяти фиксирован, и чужое выделение памяти во время
  подъёма роняет старт нехваткой памяти.
* Toolkit CUDA **12.8** (`nvcc`) и совместимый gcc (проверен 11.4): ядра sm70 собираются JIT.
* Python **3.12**; для сборки ≥ 32 ГБ ОЗУ при `MAX_JOBS=8`; ~35 ГБ диска под модель.

## Установка

```bash
git clone -b sm70 https://github.com/xormal/vllm-sm70.git
cd vllm-sm70
CUDA_HOME=/usr/local/cuda-12.8 MAX_JOBS=8 scripts/install_from_source.sh
```

Скрипт создаёт `.venv` с точными версиями пакетов боевого
([`requirements-sm70.txt`](requirements-sm70.txt)). Затем он собирает `flash-attention-v100` и vLLM под
`sm_70`; сборка vLLM идёт около часа. Если ваш конфиг pip подключает недоступные индексы, запускайте с
`PIP_CONFIG_FILE=/dev/null`.

## Запуск

```bash
huggingface-cli download alexxorm/Qwen3.8-27B-ABLITERATED-GPTQ-Int8-Clef \
    --local-dir /models/Qwen3.8-27B-ABLITERATED-GPTQ-Int8-Clef

PY=.venv/bin/python MODEL_DIR=/models/Qwen3.8-27B-ABLITERATED-GPTQ-Int8-Clef \
CARDS=0,1 PORT=8000 scripts/serve_qwen38_clef.sh
```

Пускач точно воспроизводит боевой сервер:
- подгружает 105 рычагов из [`configs/qwen38-27b-int8-clef.env`](configs/qwen38-27b-int8-clef.env);
- проверяет компилятор;
- выбирает обмен fp16 или int12 по топологии NVLink;
- отказывает, если карты или порт заняты;
- собирает все ядра одним процессом и запускает сервер с аргументами боевого.

Первый старт компилирует ядра (15–30 мин) и упаковывает веса внимания в W12. Всё это кэшируется в
`STATE_DIR`, и следующие старты занимают несколько минут. Переменные:

| Переменная | По умолчанию | |
|---|---|---|
| `MODEL_DIR` | обязательна | каталог модели; адаптеры Clef берутся из `MODEL_DIR/clef` |
| `CARDS` | `0,1` | две карты (номера nvidia-smi) |
| `HOST`, `PORT` | `0.0.0.0`, `8000` | адрес сервера |
| `SERVED_NAMES` | `Qwen3.8-27B-ABLITERATED` | имена модели в API |
| `THINK` | `false` | `enable_thinking` по умолчанию (можно менять в запросе) |
| `FA2SM70_CLEF` | `1` | `0` — только базовая модель |
| `FA2SM70_CLEF_NMAX`, `FA2SM70_CLEF_MEDIA` | `32768`, `1` | предел записи Clef в токенах; картинки в записях Clef (`0` — отказ) |
| `DRYRUN=1` | | напечатать итоговое окружение и команду, ничего не запуская |

### Clef: `POST /v1/systemone`

Формат запроса и ответа — как у Clef (SystemOne). Типы вопросов:
- `choice` — словарь вариантов;
- `score` — упорядоченный список;
- `noul` — вероятность «да».

Пределы:
- до 32 768 токенов на запись вместе с картинками (`FA2SM70_CLEF_NMAX`; собственное умолчание Clef —
  16 384, поле `"max_length"` уменьшает предел);
- до 16 картинок на запись; видео — отказ 400;
- до 64 вопросов, до 448 вариантов всего и до 256 на один вопрос;
- две записи считаются одновременно, остальные ждут.

Картинки — поле `"images"`: ссылки http(s), data-URL, голый base64 или объект как в чате
`{"image_url": {"url": ...}}`. Запись собирается как `encode_record` Clef: токены картинок стоят сразу
после `STATE:\n`. Визуальный энкодер Clef побайтово равен энкодеру этой сети (333/333 тензоров), поэтому
работает энкодер, который уже обслуживает чат. Картинки загружаются как в чате, с теми же ограничениями
доменов и путей. Воркер сверяет запись, которую получил движок (длину и контрольную сумму), с записью
эндпоинта и при расхождении отказывает.

Пример запроса и ответа — в [английском README](README.md#decisions-post-v1systemone-clef).

Устройство. Запись кодируется шаблоном Clef и идёт как префилл с одним токеном. Только на её строках
int8-ядра GEMM добавляют две поправки:
- `deabl` — ранг 1, слои 2–63;
- точную LoRA Clef ранга 256 — слои 40–63, подкачиваются из закреплённой памяти хоста.

Так обслуживаемые веса превращаются в веса Clef. Финальные скрытые состояния уходят в голову Clef на
родном CUDA. У запросов Clef свой `cache_salt`, и префикс-кэш они не читают. Код:
[`sm70/integrations/vllm_sm70/fa2sm70_clef.py`](sm70/integrations/vllm_sm70/fa2sm70_clef.py),
[`sm70/fa2_sm70/csrc/clef.cu`](sm70/fa2_sm70/csrc/clef.cu).

## Известные ограничения

* Только Volta.
* `/v1/completions` с `echo` и `logprobs` на длинном промпте занимает 1.89 ГиБ на ранг под логиты
  всего словаря и может уронить движок. Не открывайте логпробы промпта недоверенным клиентам.
* При спекуляции логпробы декода зависят от раскладки памяти при старте на уровне ~1e-3. Побайтово
  сравнимы только одинаковые конфигурации.
* Запись Clef — до 32 768 токенов. Голова сверена с PyTorch fp32 на 32 768, тест на извлечение фактов
  проходит 40/40 до 32K, но Cloudflare не оценивал Clef дальше собственного умолчания 16 384.
* Clef с картинками проверен на записях с известным ответом и на детерминизм, но ещё не по вероятностям
  против исходного Clef. В этой сети быстрый процессор изображений Qwen2-VL, у Clef — медленный: число
  токенов картинки одинаково, пиксели могут слегка отличаться. Видео в `/v1/systemone` не
  поддерживается.
* Открытые дефекты, найденные фаззингом 14.10 и в бою ещё не исправленные (VALIDATION.md, «Open
  defects»): при общих буферах GDN полный граф декода в 9 из 10 групп GDN читает устаревшее число
  принятых токенов; запись Clef, вытесненная посреди префилла, дважды накапливает средние спанов;
  дополненные строки батча черновика могут писать K/V черновика в слоты чужих запросов.
* Отбор разреженного декода держит не больше 4096 блоков ключей: при `FA2SM70_SPARSE_B=64` это таблица
  на 262 144 токена. Больший `max_model_len` или меньший блок падает на первом длинном декоде.
* Исправления после первого выпуска (инциденты 13.10, 14.10 и 18.10) перечислены в README.md, раздел
  «Changes relative to 1Cat-vLLM», п. 8; разборы — в VALIDATION.md.
